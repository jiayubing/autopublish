# 九板块客户知识库产品改造方案

状态：阶段一至四的本地实现与最终验证已完成；真实模型与搜索质量 gate 尚未执行，需要当次授权。日期：2026 年 10 月 1 日。

本方案把原来在豆包里分轮填写提示词、最后复制九板块到本地的工作自动化，并增加有目的的联网研究。最终形成一份能够发给客户、能够编辑导出、能够用于文章生成的九板块知识库。用户不需要维护另一套客户确认稿或结构化客户知识。

本方案是本次改造的唯一产品范围；下文目标分阶段落地，未完成项不得视为现有能力。2026-10-01 用户要求按本方案开始实施，三个产品取舍按方案执行。

## 产品目标

用户提供客户的基本资料和本次要求，软件理解资料、搜索补充、分析整理并创作九板块。资料丰富的客户应得到更完整、有针对性的内容；资料少的小店应得到贴合经营特点、用户需求和消费场景的内容，而不是只有原文摘录或一页缺失提示。

知识库正文是唯一的内容编辑与交付中心。后台保留必要的来源、使用限制和版本信息，以帮助文章使用内容，但这些信息不能成为另一份需要用户同步维护的正文。

成功不只意味着生成接口返回成功，还必须满足：内容值得交付、搜索有明确补充价值、文章确实能用上保存后的知识库。

## 实施前基线与改造目标

下表记录启动实施前的源码基线，不是当前功能状态；最终实现与验证见文末。

| 当前实现 | 对实际使用的影响 | 目标 |
| --- | --- | --- |
| 已有 R1 至 R5 研究和 K 成稿，最多 12 次请求、3 次搜索 | 已有自动化基础，可以复用 | 保留单条生成流程，调整研究目标和最终产物 |
| 搜索区分客户实体与决策背景；实体搜索无结果后抑制继续查同一实体 | 能避免反复搜索小店，但没有保证随后一定补充行业与场景信息 | 资料少时主动转向适合该业务的背景研究 |
| K 同时生成九板块正文和结构化知识 | 结构化字段或关联失败仍可能阻止正文成为有效知识库 | 正文保存成功不依赖辅助索引完整 |
| 页面并列九板块稿、客户知识、客户确认稿 | 用户需要理解多个相近产物 | 默认只展示和编辑九板块知识库 |
| 客户确认稿另从结构化知识重新组合 | 与真正要交付的九板块重复 | 删除这条独立生成、展示与导出路径 |
| 默认提示词偏工业企业，每板块目标 600 至 1000 字，资料不足可省略 | 小餐饮等客户容易套用不合适的框架或大量缺项 | 保留九板块，按客户业务与资料量展开 |
| 已检查的文章提示词及知识选择逻辑使用资料、问题研究和结构化条目，没有直接消费九板块正文 | 好内容写进九板块，也不一定进入文章 | 将当前有效九板块接入文章输入 |

“客户知识”目前可以包含客户资料、公开研究和分析，并非只能提取客户资料。真正的问题是它的产品地位、正文与条目的关系，以及文章如何使用；不能靠把标签改名解决。

## 生成流程

沿用现有连续研究骨架，不引入第二套生成引擎。

1. 理解客户：识别名称、地区、业务、产品服务、已有特点和资料缺口，避免把同名企业的资料混入。
2. 搜索补充：优先寻找能够确定属于客户的公开信息；公开信息少时，转向相关品类、当地消费环境、消费场景、常见疑问和选择因素。
3. 分析价值：说明已有特点对哪些人、在什么情况下有价值。普通特点可以写具体，不强行提炼成“行业领先”。
4. 创作九板块：综合原资料、搜索结果和分析，形成自然、连贯、有针对性的交付内容。
5. 本地整理并保存：修正常见格式问题，保存正文及必要来源信息；辅助索引不完整时给出提示，不能因为可选条目失败而丢掉完整正文。

默认沿用最多 12 次请求、3 次搜索的现有预算。资料少且尚无相关背景研究时，至少安排一次背景搜索尝试；搜索可合并相关问题，不承诺一定找到有用信息。搜索无结果或服务失败时，基于已有材料继续形成可用内容并记录限制，不反复重试消耗预算。最终成稿不再临时开启另一轮搜索。

内部“研究说明”展示搜了什么、补充了什么、哪些内容来自客户资料、哪些属于分析、哪些问题未解决。无需要求用户先填写另一张事实审核表。

## 信息如何使用

| 信息类型 | 知识库中的用法 | 不能做的事 |
| --- | --- | --- |
| 客户提供的经营资料 | 作为客户自述，整理、展开其业务与价值 | 将营销自述升级为独立认证 |
| 能匹配客户身份的公开信息 | 补充客户事实，内部保留来源与时间 | 仅因同名就认定属于客户 |
| 行业、品类、场景与消费研究 | 支撑用户痛点、适用场景、选择因素和内容分析 | 把行业普遍做法写成该店已经提供的服务 |
| 基于已有信息的合理分析 | 解释特点与需求的关系，用恰当语气表达 | 编造销量、年限、奖项、效果、案例或评价 |

客户事实有冲突时，不自行认定某一方正确。争议点进入内部说明，正文采用不依赖该争议的表达；不因此废弃其他可用板块。地址、营业时间、价格等易变信息不默认为永久准确。

例如，只知道一家店经营家常菜、位于社区附近，可以研究工作日就餐和家庭用餐需求，并写出这类场景下的选择考虑；不能据此写成该店提供外卖、包间、免费停车或获得居民一致好评。

## 九板块的写作规则

保留现有九个板块名称和顺序，调整展开方式。现有默认提示词作为起点，不假定它与用户历史手工版完全一致；已有自定义提示词应保留，改造不能静默覆盖。

| 板块 | 写什么 | 小店或资料少时怎么处理 |
| --- | --- | --- |
| 产品或服务描述 | 经营内容、服务对象、使用场景、选择理由 | 用已知产品与服务展开，不套用产能、精度、全产业链 |
| 产品或服务特点 | 已有特点及对顾客的实际意义 | 允许普通特点，不强行声称独有优势 |
| 品牌故事 | 有依据的经营经历、定位和理念 | 可围绕已知定位展开，不能虚构创业经历、传承或里程碑 |
| 用户痛点 | 消费场景、顾虑、选择需求及与客户的关系 | 重点使用品类与场景研究；不能把建议写成已提供的承诺 |
| 创始人介绍 | 已提供或可核实的人物经历、经营角色与理念 | 无人物材料时不编造姓名、履历或初心 |
| 社会贡献 | 有依据的公益、就业、社区或行业活动 | 不套用助残、绿色生产、人才培育等模板事实 |
| 信任背书 | 可确认的经营信息、资质、透明服务信息与相关证据 | 有什么写什么，不要求小店必须有专利、奖项或大客户 |
| 客户案例 | 有依据的对象、需求、服务与结果 | 不把假想使用场景冒充真实案例 |
| 客户评价 | 有来源的真实反馈与口碑信息 | 不伪造引语、评分、满意度或榜单 |

建议采用“九个固定编辑位置，有内容的板块进入对外交付”的规则：编辑页始终保留九个位置；确无依据的板块在内部显示缺口，默认不导出空标题和缺失说明。客户事实不足并不阻止产品、特点和痛点等板块充分展开。

这是需要重点确认的产品取舍：保留九板块框架，不承诺每个客户都能凭现有资料生成九个充实板块。如要求每次九块都有正文，应补充相应事实，或另行确认替代板块；不能通过编造凑齐。

600 至 1000 字作为资料充足板块的参考目标，不做通过门槛，不强制单个自然段。内容完整、具体、少重复优先；允许短板块和自然分段。来源编号、研究过程、校验信息不混入交付正文。

## 页面与日常操作

客户知识库页默认打开九板块正文，显示保存时间、当前版本和必要的生成状态。主要操作为“生成知识库”“编辑”“保存”“导出”；来源、研究说明、缺失信息收起到辅助区域。

删除独立“客户确认稿”入口及其专用路径。“客户知识”结构化卡片不再作为默认工作区，也不再提供与正文竞争的日常编辑入口。现有 GEO 问题能力保留为辅助入口，避免扩大到整个内容生产工作台重做。

初版保留现有 Markdown 导出，并增加一键复制完整正文；不在本次引入 Word、PDF 模板系统。导出、复制和文章读取都使用同一个已保存版本。编辑中的未保存内容不被后台文章任务读取。

首次生成成功后保存为当前版本，不增加“客户确认后才能使用”的审批环节。已有内容重新生成时，先展示新结果，用户选择替换后才成为当前版本，避免覆盖人工修改。生成失败保留旧版本及已收到的完整结果，并明确区分二者。

## 文章生成如何使用

将当前有效九板块内容接入现有文章 brief／prompt 构建链路，作为客户内容的主要来源；选题研究、文章模板和必要使用限制继续保留原职责。无需用户再次复制九板块、上传成资料文件或手动勾选每个板块。

初版优先直接使用可容纳的完整正文，避免先做复杂检索系统。超过模型输入预算时，按完整板块选取与主题相关的内容，并记录选用了哪些板块，不静默截断正文。来源与分析分类随所选内容传入，防止文章把行业背景重新写成客户事实。

每次任务使用明确的知识库版本。编辑保存影响之后新建的任务；已创建的批次保留原版本，避免同一批次中途改变依据。文章及任务记录保留知识库版本标识和实际输入快照，不反向修改知识库。

辅助索引只能从当前正文和相应来源生成；索引过期或生成失败时，回退到正文，不继续使用与正文冲突的旧条目。人工保存不隐含额外模型调用。必要的保密和禁用规则仍由现有规则所有者维护，不因正文编辑而丢失。

旧客户没有九板块时，继续保留现有资料生成能力并提示可生成知识库，不能使既有客户突然无法写文章。这个兼容行为只服务真实存量数据，不保留两个九板块生成入口。

## 改造范围与实施顺序

| 阶段 | 实施内容 | 完成条件 |
| --- | --- | --- |
| 一 内容与版本统一 | 在现有知识库存储所有者内确定正文、来源与版本合同；旧 deliverable 接入正文；保护已有修改 | 单一可编辑正文，重启后可恢复，失败不覆盖旧版本 |
| 二 研究与成稿调整 | 改善弱资料搜索分配、九板块写法、格式容错；辅助索引失败与正文保存分离 | 丰富资料与小店样例均形成可用内容，来源与事实不混淆 |
| 三 页面收敛 | 九板块编辑与复制导出，移除客户确认稿及无消费者的接口、类型、测试和实现 | 用户只维护一份正文，辅助信息不干扰交付 |
| 四 文章接入与验收 | 修改现有 brief 与任务输入，统一版本和上下文，验证存量客户行为 | 九板块内容实际进入文章提示词，版本冻结有效 |

全程串行实施。复用现有 continuous run、knowledge application/store、renderer feature 和文章编排；不增加第二个知识库存储或旁路 writer。存量结构化事实、人工锁定和来源不能直接删除；迁移时保留并映射，不能让旧条目静默覆盖新正文。

当前工作索引中的 CP-5 等计划不因本方案自动推进。用户确认后，以本方案为这次改造的单一产品范围，明确与现有合同冲突的替代条款，再制定最小实施任务。新正文权威与旧结构化合同的变化需要在同次实施中更新相关规格、测试和调用方。

本次不改投稿、发布、订单流程，不引入协作审批、向量数据库或独立知识库后台，不进行真实数据删除与自动收费重试。

## 验收方式

| 场景 | 必须观察到的结果 |
| --- | --- |
| 资料丰富的客户 | 九板块忠于资料并有有效展开，不只是复制和同义重复 |
| 仅有简单介绍的小餐饮店 | 安排相关背景搜索，产品、特点、痛点等板块体现具体消费需求，不套工业模板 |
| 网上找不到该店 | 停止重复实体搜索，转向背景研究；不混入同名店资料 |
| 没有创始人、案例或评价 | 不编造；内部保留缺口，导出不夹带写稿说明 |
| JSON 小格式错误或辅助关联缺失 | 有效正文仍可保存，问题说明具体，不只报一个 schema 错误 |
| 搜索失败或整体生成失败 | 显示真实状态，旧版本仍可用，完整已收结果可查看，不盲目重试 |
| 修改九板块并保存 | 预览、复制、导出一致；新文章任务拿到新版本 |
| 批次创建后再编辑 | 批次继续使用创建时版本，不混入后续改动 |
| 辅助索引过期 | 文章使用有效正文，不使用冲突旧条目 |
| 存量客户与人工修改 | 不丢失旧内容，不自动覆盖锁定事实；没有九板块也不会突然失去文章生成能力 |

自动化测试用合成资料与假搜索，覆盖正文保存、版本、失败恢复和实际 prompt 输入；页面验证加载、空态、编辑、失败和导出。真实内容质量由资料丰富客户与小店各一例人工对照验收，重点看具体性、增量价值、可交付性和事实边界。真实模型及搜索验收另需当次授权，自动化通过不等于真实写作质量已达标。

## 实施记录：阶段一

### 合同替代与当前边界

- 替代 GEO V2 / CP 既有“重新生成直接替换九板块正文”的行为：首次成稿成为当前正文；已有正文时保存 `pendingDeliverable`，用户显式替换才更新正文。当前正文、候选、来源和结构化事实在同一个 GeoKnowledgeStore JSON 中原子保存，不新增 writer。
- `revision` 继续负责整份知识库的并发控制；`deliverable.contentRevision` 只在正文编辑或替换时递增。`savedAt`、`origin`、`sourceIds`、`indexStatus` 记录正文保存时间、来源类别和辅助索引状态。旧 deliverable 读取时映射为正文版本1，不读取即写盘或破坏原文。
- 手工正文保存不调用模型、不覆盖锁定事实或使用限制；辅助索引标为 stale。候选采用唯一 `candidateId`，替换同时校验文档 revision，拒绝迟到或重复提交。相同正文保存是无副作用 no-op。
- 阶段一仍保留旧结构化合并、客户确认稿和文章读取路径；这些是阶段三、四的明确移除/替换对象，不能把阶段一测试当作正文已经用于文章的证据。阶段二仍需拆开辅助索引失败与正文保存。

- Store/schema/application：正文版本、候选保存和显式替换，保持单文件原子性、已有来源与人工锁定；失败保留当前版本。
- Service → IPC → preload → bridge → feature：增加受控正文保存和候选替换操作。
- 页面提供版本/保存时间、正文编辑保存、复制已保存正文、候选预览/替换；未验证失败结果与当前正文分开展示，未保存编辑不进入预览或导出。
