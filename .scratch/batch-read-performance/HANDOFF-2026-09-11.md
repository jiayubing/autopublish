# 批量读取与豆包进度局部优化

基线：4c656f08。用户明确选择保留批量生成现有恢复协议，仅做局部优化。未提交或推送。

## 已实施

- client-knowledge：单工作区缓存客户目录列表及 metadata。根目录 stat 变化时重新枚举；每次查询仍验证路径边界、逐个 stat metadata，变化时重新读取。新客户、ID 修改及重复 ID 仍可检测。避免重复 readdir/read/JSON.parse，但不是 O(1) 身份查询。
- generation-batch-file-store：只缓存最近一个批次的已解析数据，stat 变化则重读；返回独立副本。恢复检查与真实状态变化的原子写入/fsync 保持不变。
- generation-batch-store：同值批次状态和重复成功确认不再写入。仍保留不同文章成功确认的冲突检查。
- 豆包队列：countdown 不携带 tasks；完整查询及任务状态事件仍携带任务列表。IPC 事件 tasks 可省略，查询结果合同仍要求 tasks。Renderer 仅合并剩余时间并保持 tasks 引用，倒计时不会取消初始完整查询。

## 保留与后续 owner

- 批量生成真实状态变化仍重写整批 JSON；彻底解决该结构性成本属于 generation-batch-file-store 的存储改造，用户明确选择本轮不做。
- 跨客户 preview/admission 保留。regular-queue-application 当前明确要求单客户（已有合同测试），cross-client 应用负责分组、部分成功和提交不确定性。不能把单客户读写接口直接合并成跨客户事务。本轮身份 metadata 缓存也会帮助其客户解析，但不声称消除了 preview/admission 重复读取。
- removal 历史查询仍全量，后续 owner 为 article-removal-transaction-store 与 article-mutation-kernel；没有引入第二套历史索引或长期无界正文缓存。
- hepan 最终 inspection 例外保留，后续 owner 为 regular-platform-preparation-port 和平台准备合同；本轮没有改变账号验证语义。
