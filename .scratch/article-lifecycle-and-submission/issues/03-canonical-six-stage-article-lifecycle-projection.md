# 03 — 六类文章生命周期统一投影

**What to build:** 由文章、投稿队列、发布事实、服务商订单和删除事实统一派生六个互斥入口及可执行动作，让文章管理、导航数量和其他界面消费同一份业务判断。

**Blocked by:** None — can start immediately

**Status:** `COMPLETE`（以 `ARTICLE-LIFECYCLE-WAVE-EXECUTION-PLAN.md` 的实时 provenance 为准）；不得重复调度

## 启动约定

- 阅读权威规格中全部分类优先级、编辑权限和测试决策；不得把六类入口写回文章文件或数据库状态字段。
- 盘点当前主进程投影、Renderer 再次派生逻辑、导航计数和需处理投影，先用组合测试记录冲突行为。

## 执行过程

1. 定义文章事实输入、六类阶段、锁定原因、主要动作、批量动作和安全解释文本的版本化只读契约。
2. 明确唯一优先级：可信发布成功优先于售后/退稿，结果不确定始终冻结，活动订单优先于待投稿，回收站由删除事实决定。
3. 建立集中分类器和批量投影服务，一次读取一批文章及关联事实，禁止逐文章访问数据库或磁盘。
4. 让文章管理快照和导航数量使用该投影；Renderer 只展示阶段和动作，不重新计算状态机。
5. 暂时兼容旧事实输入，但把兼容映射集中在边界，并标记供 23、24 收缩。
6. 增加所有优先级组合、互斥性、计数一致性、权限一致性和大批量性能测试。

## 职责边界

- 分类器是“文章属于哪个入口、允许哪些动作”的唯一所有者。
- 事实读取器负责批量装载，不解释业务状态。
- Renderer 只消费投影，不查看底层 publication/order/batch 状态决定按钮。
- 导航汇总只聚合投影结果，不拥有另一套分类规则。

## 架构硬门槛

- 分类核心保持纯函数和小接口，目标不超过 250 行；事实装载与界面投影分别独立。
- 新文件不得超过 400 行，禁止新增长度例外；现有超长快照模块不得继续增长。
- 阶段标签与底层事实解耦，未来改名不能要求迁移历史数据。
- 错误/未知事实采取失败关闭策略，不允许默认归入待投稿。
- 测试只断言输入事实到外部投影，不锁定内部函数或文件。

## Acceptance criteria

- [ ] 每篇文章恰好进入待投稿、投稿队列、付费处理中、需处理、已发布或回收站之一。
- [ ] 所有文章列表、导航数量和动作权限来自同一投影结果。
- [ ] 发布成功、退稿、售后、活动订单、不确定结果和回收事实的组合优先级符合规格。
- [ ] 六类名称不是持久化状态，标签改名不会改写历史数据。
- [ ] 批量投影不存在逐文章数据库/磁盘查询，容量基准没有明显回退。
- [ ] 交接记录说明事实输入、优先级、动作策略、兼容映射和模块行数。

## Non-goals

- 不在本 ticket 改写普通平台或网站媒体的写入流程。
- 不移除审核字段或旧状态，只集中兼容读取。
