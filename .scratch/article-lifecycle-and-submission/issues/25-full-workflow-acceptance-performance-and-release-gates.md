# 25 — 全流程验收、性能与交付门禁

**What to build:** 对新文章生命周期、普通平台、网站媒体、图片、迁移和删除流程进行独立端到端验收，建立可持续的性能、架构、类型和打包门禁，并给出人工验收交接。

**Blocked by:** 24 — 收缩并删除全部旧业务规则

**Status:** ready-for-agent

## 启动约定

- 本 ticket 以独立审计者视角执行，不以各 ticket 自报完成代替证据。
- 自动化不得使用真实服务商、真实付费订单或真实平台账号；真实验证只生成用户可执行清单，不自行触发外部费用或发布。

## 执行过程

1. 建立规格 85 条 user stories 到行为测试/人工验收的追踪矩阵，明确自动、模拟和用户控制三类证据。
2. 验证六类入口互斥、导航计数和操作权限；覆盖成功高于售后/退稿、uncertain 永远冻结等组合。
3. 用假平台运行至少两个普通平台组并行，验证同组 FIFO、追加、开始/暂停、重启暂停、错误范围和人工 uncertain 收口。
4. 用假供应商验证付费确认、价格变化、串行扣费、订单号门槛、暂停、未知结果、订单刷新、取消和永久历史。
5. 验证三个普通平台 0–5 图片路径、客户隔离、布局、失败降级和纯文本；网站媒体图片明确保持未支持状态。
6. 对合成旧库执行 dry-run、迁移、重开、备份恢复和冲突需处理验证。
7. 运行大批量文章/队列/订单投影基准，证明无 N+1；运行模块尺寸、依赖方向、legacy absence、安全、typed IPC、全测试、Renderer build 和生产打包门禁。
8. 输出剩余风险和人工验收清单，包括真实两平台并行、真实订单状态刷新，以及未来网站媒体图片专项试验。

## 职责边界

- 验收测试只通过公开应用/bridge 接缝观察行为，不访问私有函数和内部表结构。
- 合同测试可使用供应商传输边界，但不穿透应用状态机。
- 性能基准测量批量接口和用户可感知快照，不以微基准替代。
- 本 ticket 发现缺陷时记录并在对应所有者模块修复，不建立新的“验收补丁”巨型模块。

## 架构硬门槛

- 所有新生产模块不超过 400 行且无新长度例外；核心领域/应用模块优先不超过 300 行。
- 原 2031 行投稿服务必须已收缩为薄门面，现有被触及的超长 Renderer/contract 模块不得增长并应有拆分证据。
- 依赖方向、模块职责和公开接口由静态门禁与审计表共同证明。
- 不以跳过、放宽断言、提高超时或排除测试换取绿色结果。

## Acceptance criteria

- [ ] 85 条 user stories 全部映射到自动化、模拟或明确的用户控制证据。
- [ ] 六类文章入口、普通平台并行链和网站媒体订单链端到端通过。
- [ ] 图片、迁移、删除恢复、unknown/uncertain 和故障注入场景通过。
- [ ] 批量投影没有 N+1，性能基准满足既有预算或提供经批准的新预算依据。
- [ ] 模块尺寸、依赖方向、legacy absence、安全、typed IPC、全测试、构建和打包门禁全部通过。
- [ ] 真实外部验证清单明确说明费用/发布风险、前置配置、记录字段和停止条件。
- [ ] 最终交接包含追踪矩阵、测试计数、性能数据、模块行数、残余风险和未实现的网站媒体图片事实。

## Non-goals

- 不自行创建真实付费订单、登录真实平台或发布真实文章。
- 不把网站媒体图片传输标记为已实现。
