# 01 — 投稿准备与批次生命周期深模块

**What to build:** 在不改变现有用户行为的前提下，把文章投稿预检、单目标批次创建和队列读取从投稿服务巨型模块中分离，形成后续普通平台与网站媒体流程都能复用的稳定应用边界。

**Blocked by:** None — can start immediately

**Status:** ready-for-agent

## 启动约定

- 先完整阅读仓库根目录的《文章生命周期与投稿流程规格》、权威业务词汇表和已接受 ADR；本 ticket 只改变内部结构，不提前实现后续业务规则。
- 确认工作树基于包含本规格的提交且没有混入其他 ticket 的未提交修改。
- 先用现有测试固定预检、批次创建、幂等、账号绑定、队列读取和错误码行为，再移动实现。

## 执行过程

1. 盘点投稿服务对外公开命令、直接调用方、持久化端口和文件队列副作用，画出“预检 → 创建批次 → 读取批次”的最小调用链。
2. 定义一个薄的投稿应用门面，以及分别负责资格预检、批次规划、批次提交和只读查询的内部端口；端口只传输文章身份、目标身份和明确结果对象。
3. 先把新模块放在旧实现旁边，通过门面转发保持行为和 IPC 契约不变。
4. 迁移预检、单目标任务展开、账号绑定校验、幂等判断、批次写入和列表查询；不得顺带迁移删除、清理、恢复或失败重试。
5. 删除已经迁出的重复分支，确保同一规则只剩一个所有者。
6. 运行投稿、账号绑定、SQLite 批次、typed IPC、打包边界和 Phase 8 门禁测试。

## 职责边界

- 投稿资格模块只回答“能否入队及原因”，不写数据库、不创建文件、不调用远端。
- 批次规划模块只生成确定计划，不执行副作用。
- 批次提交模块负责原子持久化与幂等，不解释界面状态。
- 查询模块只生成只读结果，不修复数据。
- 门面只编排，不复制业务判断；Renderer、供应商适配器和 SQLite 细节不得反向进入这些模块。

## 架构硬门槛

- 新生产模块目标不超过 300 行，任何新文件不得超过现有 400 行门禁；禁止新增模块长度例外。
- 每个模块只有一个主要变化原因，公开接口保持少而稳定；内部数据结构不得跨模块共享后再被修改。
- 依赖方向保持“界面/IPC → 应用服务 → 领域策略/端口 → 基础设施”，禁止反向依赖。
- 不使用一个新的“通用工具”模块承接杂项；重复逻辑必须有明确领域归属。
- 测试验证可观察行为和端口契约，不锁定私有函数名或新文件布局。

## Acceptance criteria

- [ ] 现有投稿预检、批次创建、幂等、账号绑定和批次查询行为保持不变。
- [ ] 预检、规划、持久化和查询各有单一明确所有者，旧巨型服务不再包含其重复实现。
- [ ] 新门面不暴露文件路径、SQLite 语句或 Renderer 类型。
- [ ] 新增/修改模块满足代码规模门禁，且巨型服务总行数有可量化下降。
- [ ] 相关单元、集成、typed IPC、打包和 Phase 8 门禁全部通过。
- [ ] 交接记录列出公开接口、依赖方向、迁出职责、剩余巨型职责和各文件行数。

## Non-goals

- 不移除审核、多目标或 `submitted` 旧规则。
- 不改变任何界面文案或远端投稿行为。
- 不处理队列删除、失败清理、文章回收和恢复。
