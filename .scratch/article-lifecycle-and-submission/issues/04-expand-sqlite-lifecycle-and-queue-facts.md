# 04 — 扩展 SQLite 生命周期与队列事实

**What to build:** 扩展内容库 SQLite，使其能权威保存单一活动目标、普通平台队列组、付费批次、订单快照和人工核对事实，同时提供安全的前滚迁移、验证和恢复证明。

**Blocked by:** 03 — 六类文章生命周期统一投影

**Status:** `COMPLETE`（以 `ARTICLE-LIFECYCLE-WAVE-EXECUTION-PLAN.md` 的实时 provenance 为准）；不得重复调度

## 启动约定

- 先确认 03 已冻结事实输入契约和分类优先级；数据库只保存事实，不保存六类界面阶段。
- 遵守 SQLite 权威运行状态 ADR：远端调用前提交 durable intent，远端结果返回后再提交 observation，绝不把远端调用包进事务。

## 执行过程

1. 根据 03 的事实契约设计下一版本 schema：活动目标唯一约束、队列组暂停意图、付费批次确认快照、订单显示快照、人工核对事实和必要索引。
2. 保留旧表可读，先扩展新表/列和新存储端口；迁移阶段不得让旧版本继续写升级后的内容库。
3. 实现事务化迁移、dry-run、结构验证、数据哈希验证、故障注入和恢复检查。
4. 为文章批量读取关联队列、发布和订单事实提供集合查询，避免投影出现 N+1。
5. 对活动目标和订单号建立数据库级唯一性/一致性保护，同时在应用层返回安全业务错误。
6. 更新容量、备份恢复、未来版本拒绝、只读验证和打包环境测试。

## 职责边界

- Schema 只表达持久事实与一致性约束，不解释用户界面阶段。
- 各 aggregate 只拥有一个聚合边界；提交批次、发布尝试和服务商订单不得再次合并成巨型存储模块。
- 迁移器只转换/验证数据，不调用业务服务或远端 API。
- 应用服务通过端口使用存储，不包含 SQL。

## 架构硬门槛

- 新 aggregate 目标不超过 300 行、硬上限 400 行；禁止把所有新表塞入现有超长 aggregate。
- 新增索引必须有对应查询与容量证据；禁止为猜测中的未来功能加入字段。
- 迁移必须幂等、可 dry-run、失败不留下半升级数据库。
- 所有外部返回均为稳定领域 DTO，不泄漏行对象和 SQL 错误。

## Acceptance criteria

- [ ] SQLite 能表达规格要求的活动目标、队列组、付费批次、订单快照和人工核对事实。
- [ ] 同一文章不能同时建立两个活动发布目标，且并发写入也被阻止。
- [ ] 远端 intent 与 outcome 分两次持久事务记录。
- [ ] 迁移 dry-run、真实迁移、故障回滚、重开验证、备份恢复和未来版本拒绝测试通过。
- [ ] 批量事实读取满足 03 的性能接缝，不产生 N+1。
- [ ] 交接记录包含 schema 版本、约束、索引、端口、迁移证据和模块行数。

## Non-goals

- 不迁移全部历史业务数据；完整旧数据解释由 23 完成。
- 不实现任何 Renderer 页面或远端调用。
