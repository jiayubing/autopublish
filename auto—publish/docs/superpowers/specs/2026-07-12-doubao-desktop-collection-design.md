# 豆包桌面端采集功能设计

## 目标

在 AutoPublish 桌面端内完成豆包问题维护、单条采集、批量采集、手动修正和多回答文章生成闭环。正式功能复用现有 Node/Playwright 运行层，不依赖 `F:\携程` 的 Python、CSV 或 SQLite；旧项目仅作为页面行为和选择器研究参考。

## 范围

第一版包含：

- 一个客户维护多个豆包问题。
- 在桌面端新增、编辑、启用、停用和删除问题。
- 兼容导入客户目录中的 `search_query.txt`。
- 单问题采集和跨客户、跨问题批量采集。
- 同一问题手动重新采集并直接覆盖当前结果。
- 独立、可见、持久化的豆包浏览器登录会话。
- 批量任务串行执行，任务间随机等待 15 到 30 秒。
- 暂停、继续、停止以及只重试失败任务。
- 自动采集失败后的回答和参考资料手动录入。
- 生成文章时选择一条或多条有效豆包回答。

第一版不包含：

- 采集结果版本历史和旧版本恢复。
- 多浏览器并发采集。
- 应用重启后自动恢复未完成队列。
- 豆包普通模式、联网模式或深入研究模式切换。
- 自动发布到携程或其他内容平台。

## 架构决策

采用现有 Node/Playwright 运行层，并创建独立的 `doubao` 持久会话。采集功能按职责拆分，不将页面选择器、任务队列、文件存储或 React 状态混入同一模块。

```text
React 豆包采集工作台
  -> preload API（仅客户 ID、问题 ID 和操作命令）
  -> IPC validation
  -> Doubao collection service
      -> collection queue
      -> browser adapter
      -> question store
      -> research store
  -> workspace/browser/doubao
```

模块职责：

- `question-store`：客户问题的增删改查、兼容导入和原子写入。
- `doubao-browser-adapter`：登录检测、新建对话、发送问题、等待完成、提取正文和参考资料。
- `doubao-collection-service`：单条采集、重新采集、手工录入、结果校验和持久化编排。
- `doubao-collection-queue`：批量任务状态、串行调度、随机等待、暂停、继续、停止和失败重试。
- `research-store`：采集结果的唯一正式存储。
- IPC/preload：暴露稳定、最小化的命令和事件契约。
- React：展示和发出用户操作，不直接读取文件、控制浏览器或访问豆包。

## 工作区与数据模型

工作区增加以下数据：

```text
workspace/
|-- clients/
|   `-- <client-id>/
|       |-- questions.json
|       `-- <knowledge files>
|-- research/
|   `-- <client-id>/
|       `-- <question-id>.json
|-- browser/
|   `-- doubao/
`-- logs/
    `-- doubao-diagnostics/
```

`questions.json` 是问题配置的正式写入目标。每个问题至少包含：

```json
{
  "id": "stable-question-id",
  "text": "用户在豆包中搜索的问题",
  "enabled": true,
  "createdAt": "2026-07-12T00:00:00.000Z",
  "updatedAt": "2026-07-12T00:00:00.000Z"
}
```

问题文本去除首尾空白后必须为 1 到 2000 个字符。同一客户内，对问题文本执行首尾空白清理和连续空白折叠后，不允许出现重复问题；不同客户可以使用相同问题。单次批量提交最多包含 500 个任务，超过时由主进程拒绝并要求分批。

首次读取没有 `questions.json` 的旧客户时，将非空 `search_query.txt` 导入为一个稳定问题。导入成功后，后续桌面端写入只更新 `questions.json`，不再修改 `search_query.txt`。

每个 research 文件继续使用 `research/<client-id>/<question-id>.json`。自动或手动保存的数据至少包含稳定问题 ID、问题文本、回答正文、参考资料、采集时间、采集方式和完整性状态。重新采集成功后原子覆盖当前 research；重新采集失败不得覆盖已有成功结果。

删除已有 research 或已被文章引用的问题时必须二次确认。第一版删除问题配置和当前 research，但已生成文章保留来源快照。

## 浏览器会话与登录

豆包使用名为 `doubao` 的独立 Playwright 会话和独立 profile，不复用媒体、猎炬、头条或河畔会话。浏览器必须可见，以支持扫码登录、验证码和人工观察。

登录状态为：

- `unknown`：尚未检测。
- `login_required`：需要用户扫码登录。
- `authenticated`：可以输入并发送问题。
- `session_error`：浏览器或页面状态异常。

用户点击“打开豆包登录”后启动并导航到豆包网页版。桌面端检测到可用输入框后标记登录成功。关闭 AutoPublish 时停止自动化任务；持久 profile 保留，以便下次复用登录状态。

豆包网页版当前无需显式启用联网或深入研究模式。采集器不得查找、点击或依赖此类模式按钮。

## 自动采集与页面提取

每次采集使用新对话，避免历史上下文影响回答。适配器先记录本次问题对应的页面节点，再提取其后的最新豆包回答节点。定位优先级为语义属性、可访问性角色、稳定文本和消息之间的结构关系；动态 class 只能作为最后兜底。不得把整个消息列表的文本当作当前回答。

参考资料只从当前回答关联的参考资料入口提取，不能扫描全页外部链接。参考资料允许为零条；存在时只接受合法 HTTP 或 HTTPS URL，并统一为 `title`、`url`、`snippet`。

回答完成必须同时满足：

- 已出现非空回答节点。
- 回答去除首尾空白后至少包含 10 个字符。
- 页面不再显示正在生成或停止生成状态。
- 回答文本连续多次保持稳定。
- 页面没有登录失效、验证码、网络错误或豆包错误提示。

自动采集成功要求回答正文通过有效性校验，问题文本与任务一致，且结果可被 research store 保存。自动和手动回答正文均不得超过 200000 个字符。页面有回答但无法定位正文、回答为空或超时均为失败，不得保存空 research。

失败错误至少区分：需要登录、找不到输入框、回答生成超时、无法定位正文、回答为空、验证码或访问限制、浏览器会话异常。

失败时可保存一张诊断截图和脱敏页面结构摘要到 workspace 日志目录。诊断数据默认最多保留最近 20 次，不保存 Cookie、Local Storage 或完整 HTML。

## 单条与批量任务

最小任务单位为 `clientId + questionId`。单条采集和批量采集必须调用同一个 collection service，避免出现两套页面提取逻辑。

队列状态为：

```text
pending
waiting_login
running
waiting_interval
paused
succeeded
failed
cancelled
```

批量规则：

- 同一时间只允许一个豆包队列运行。
- 所有任务串行执行。
- 两个任务之间随机等待 15 到 30 秒。
- 暂停在当前回答完成并保存后生效，不强行截断流式回答。
- 停止阻止后续任务启动；当前任务尽量安全结束，未开始任务标记为取消。
- 继续从剩余待处理任务开始。
- “重试失败”只重新加入失败项，不重复成功项。
- 手动重新采集明确忽略已有结果，但仅在新结果成功后覆盖旧结果。
- 第一版不持久化未完成队列；应用重启后已保存结果仍然存在。

队列通过主进程事件向 renderer 推送状态。事件只包含任务 ID、客户 ID、问题 ID、状态、进度、等待秒数、回答字数、参考资料数量及安全错误信息，不包含 Cookie、完整 DOM 或浏览器存储。

## 手动录入与修正

自动采集失败或结果需要修正时，用户可以在桌面端编辑回答正文，并新增、编辑或删除参考资料。手动内容使用与自动结果相同的校验和 research store，不建立第二套存储。

手动保存必须记录采集方式 `manual`；自动采集记录 `automatic`。空回答、非法 URL 或与客户不匹配的问题 ID必须拒绝。

## 桌面端体验

现有“AI内容生成”工作台扩展为三个标签页：

1. 问题与采集
2. 文章生成
3. 已生成文章

“问题与采集”采用客户、问题和回答三栏结构：

- 客户栏支持单选浏览和多选批量，显示问题总数、成功数和失败数。
- 问题栏支持新增、编辑、删除、启用、停用、勾选、单条采集和重新采集。
- 回答栏展示完整回答、当前问题的参考资料、采集时间、采集方式和状态，并提供手动修正。
- 页面底部固定任务区展示当前任务、总体进度、等待倒计时和暂停、继续、停止、重试失败命令。
- 登录区展示当前状态，并提供“打开豆包登录”。

界面不使用嵌套卡片，不让动态状态改变工具栏或进度区域尺寸。危险操作使用明确确认弹窗，图标按钮提供工具提示。

## 多回答文章生成

文章生成页面只列出存在有效回答的问题，并允许选择一条或多条。生成请求从单个 `researchQueryId` 演进为 `researchQueryIds`，同时在过渡期兼容已有单条文章记录。

Prompt 按问题分别组织：

```text
问题 1
回答
参考资料

问题 2
回答
参考资料
```

多条回答不能先拼接成失去来源边界的大段文本。界面展示所选问题数量和预计输入总字数。空回答必须在调用 AI 前阻断。

生成文章的 metadata 为每条来源保存不可变快照：问题 ID、问题文本、回答正文、参考资料、采集时间和采集方式。问题后来被重新采集或删除时，已经保存的文章正文和来源快照不被静默修改。

## 安全与错误处理

- Renderer 只能提交客户 ID、问题 ID、问题字段和明确命令，不能提交任意文件路径、浏览器 profile 路径或页面脚本。
- 主进程重新解析并校验所有客户、问题和 research 路径。
- 客户 ID、问题 ID、URL、回答正文和批量任务数量都必须校验。
- 浏览器 Cookie、Local Storage、API Key、客户资料正文和完整页面 DOM 不得进入 IPC 错误、普通日志或诊断摘要。
- 采集错误使用稳定错误码；界面展示可操作的中文说明，不暴露内部命令和绝对工具路径。
- 应用关闭、任务停止和浏览器异常必须产生唯一终态，并清理 timer、监听器和子进程控制句柄。

## 测试策略

### 问题存储

验证多问题增删改查、稳定 ID、重复问题、启用状态、非法客户 ID、原子写入、路径逃逸、`search_query.txt` 兼容导入和重复读取幂等。

### 页面解析

使用脱敏豆包页面 fixture 验证完整回答、流式回答、零参考资料、多轮对话、登录失效、验证码、错误提示和页面结构变化。fixture 不包含真实客户问题、Cookie 或账号数据。

### 采集服务与队列

注入 fake browser adapter 和可控时钟，验证单条成功、失败不覆盖、覆盖重采、手工保存、串行顺序、15 到 30 秒随机等待、暂停、继续、停止、失败重试、事件顺序和禁止双队列。

### IPC 与 React

验证 IPC 参数边界、错误封装和事件退订；验证问题维护、登录状态、单条与批量命令、任务进度、人工录入以及多回答选择。Renderer 回归测试必须证明前端不直接读取文件或控制浏览器。

### 文章生成

验证多个 research 进入 Prompt、引用按问题分组、空回答阻断、旧单条 metadata 兼容，以及新文章保存全部问题 ID、采集时间和来源快照。

### 发布前真实冒烟

1. 为测试客户新建三个问题。
2. 首次扫码登录并确认重启后登录状态可复用。
3. 单独采集一个问题，确认回答不为零字且与页面可见正文一致。
4. 批量采集剩余问题，验证串行进度和随机等待。
5. 分别验证暂停、继续、停止和只重试失败项。
6. 对同一问题重新采集，确认成功覆盖、失败保留旧结果。
7. 手动修改回答和参考资料。
8. 勾选两条回答生成并保存文章。
9. 重启桌面端，确认问题、回答、登录状态和文章仍然存在。
10. 执行完整测试、Renderer 构建、项目验证和 alpha 包内容检查。

## 验收标准

- 自动采集结果与豆包页面当前回答一致，不再出现页面有完整回答但保存零字。
- 当前回答存在参考资料时正确关联；没有参考资料时仍可成功保存。
- 单条和批量采集共用相同提取和存储逻辑。
- 批量任务不并发操作豆包，不自动重复覆盖成功项。
- 失败、停止或应用关闭不产生空 research，也不破坏已有成功结果。
- 用户可以在桌面端完整维护多个问题并手动修正采集结果。
- 用户可以选择一条或多条回答生成文章，文章保留明确来源边界。
- 客户资料、问题、豆包回答、模板、文章生成和待投稿导出形成闭环。
- alpha 安装包不包含 `.env`、客户数据、豆包 Cookie、真实诊断数据或测试 fixture。
- `npm test`、renderer lint、renderer build、`npm run verify` 和 alpha 包检查全部通过。
